# Authorization

Executable OpenFGA authorization model and permission cases.

- `model.fga`: model v2 (schema 1.1), additive over v1 (every v1 type and relation is unchanged).
  - v1: `user` (`delegate`), `agent` (`acts_for`) and `profile` (`owner`, computed `owner_agent` = `delegate from owner`, `contribute`, `view_only_me`). An `agent` object ID is an `agent_delegations.id`, not the global `agents.id`. Profile creation writes only `owner`; `owner_agent` is never written.
  - Agent connect writes `acts_for`, `delegate` and `platform:revel#connected_agent` (no profile needed); disconnect deletes all three. `platform:revel` exists because OpenFGA rejects `delegate from public_viewer` over a `[user:*]` tupleset, and `agent:*` would also match disconnected delegations.
  - `profile` tiers: written `trusted`, `connection` (`[user]`), `public_viewer` (`[user:*, platform#connected_agent]`) and `blocked` (`[user]`); computed `view_trusted` > `view_connections` > `view_public`, each including the higher tiers plus the owner and owner's agents. A user's agents inherit the user's tier (`delegate from trusted|connection|blocked`). `profile:<B>#blocked@user:<A>` removes A and A's agents from every tier on B's profile, Public included, even with a stale grant; it is directional and never applies to the owner.
  - `question`: written `about` (`[profile]`) and `requester` (`[user]`); computed `requester_agent`, `respond` (= `owner_agent from about`) and `read_answer` (owner side always; requester and requester's agents unless the owner blocked the requester). `read_answer` does not follow the requester's tier: it survives revoking the requester's connection (only a block removes it), so F7 (#20) must re-check, when releasing an answer, that the requester can still see the facts it relies on.
- `tests/negative/*.fga.yaml`: cases the CLI must reject (direct writes of computed relations, agents in `trusted`/`connection`/`requester`, an `agent:*` `public_viewer`).
- `tests/*.fga.yaml`: OpenFGA CLI test cases (tuples, checks, list_objects).
- `model.json`: the committed JSON form of `model.fga`, produced by `scripts/generate-model-json.sh` (pinned CLI `model transform`). The backend bootstrap writes this file, so deploying the model needs neither Docker nor a DSL parser (the Python SDK has no DSL transformer). Regenerate it whenever `model.fga` changes.
- `scripts/test-model.sh`: validates the model, runs all tests with the pinned CLI image `openfga/cli:v0.8.2` via Docker, and fails if `model.json` is stale; exits non-zero on failure.

Run from the repository root: `bash authorization/scripts/test-model.sh` (requires Docker).

## Runtime service (backend)

- `backend/src/revel/auth/fga.py`: `create_fga_client(settings)` (stored at `app.state.fga`), idempotent tuple writes/deletes, checks. `OPENFGA_GOOGLE_AUTH=true` sends a Google ID token with audience `OPENFGA_API_URL`.
- `backend/src/revel/auth/authz.py`: subject mapping (`agent:<delegation_id>` when a delegation is active, else `user:<user_id>`; inconsistent principals are denied), module-level hooks over the client installed by `configure_authz` (app lifespan), reconciliation helpers, `can_contribute`/`require_contribute`, `resolve_viewer_tier` (checks `view_only_me`, `view_trusted`, `view_connections`, `view_public` with higher consistency and stops at the first held)/`require_viewer`. Checks raise when OpenFGA is unconfigured.
- Hooks: every hook is keyword-only, idempotent, OpenFGA-only (no database access) and bounded by `HOOK_TIMEOUT_SECONDS`. WHEN the caller awaits it, relative to its own commit, is part of the contract (the module docstring is authoritative):
  - PRE-COMMIT, inside the changing transaction; a raise rolls the row back. Unconfigured OpenFGA raises for revokes.
    - Revokes: `on_agent_disconnected(user_id, delegation_id, agent_id=None)` (F2), `on_connection_tier_changing(profile_id, viewer_user_id, tier)` (F6, on every approval or tier change: deletes any tier above `tier`, the revoke part of a downgrade, a no-op otherwise), `on_connection_revoked(profile_id, viewer_user_id)` (F6, both tiers), `on_blocked(profile_id, blocked_user_id)` (F6: writes `blocked` and deletes both tiers, so an unblock never restores a tier), `on_public_opt_in_changed(profile_id, enabled=False)` (F5). A rollback after a revoke only over-denies; a revoke after commit would leave access live meanwhile.
    - Row write FIRST: run the changing UPDATE/INSERT on `connection_requests`, `contribution_policies` or `agent_delegations` BEFORE awaiting any revoke hook, in the same transaction (flush ORM changes first), so the transaction holds ROW EXCLUSIVE before the tuple is deleted. Otherwise a concurrent `fga_reconcile` can re-grant from its earlier snapshot, find the row unchanged at its barrier and leave the revoked access live until the next run (every 15 minutes). On `connection_requests` and `contribution_policies` the barrier (EXCLUSIVE there) also waits for a `SELECT ... FOR UPDATE` row lock; on `agent_delegations` (SHARE) it does not, and an advisory lock, or no lock, never orders a writer against reconcile: such callers rely entirely on this rule.
    - Lock order (the barrier locks `connection_requests`, then `contribution_policies`, then `agent_delegations`): never write or row-lock `connection_requests` AFTER writing `contribution_policies`, `claims` or `claim_events` in the same transaction (do it first, or separately), and keep transactions that write `agent_delegations` to that table alone (F2's do). Otherwise the barrier and the writer can deadlock and Postgres aborts one of them.
    - Required order, per flow: F6 approve or tier change: UPDATE row -> `on_connection_tier_changing(tier=new)` -> commit -> `on_connection_granted(tier=new)`. F6 revoke: UPDATE row -> `on_connection_revoked` -> commit. F6 block: UPDATE/INSERT row -> `on_blocked` -> commit. F5 Public opt-out: INSERT the new policy version -> `on_public_opt_in_changed(enabled=False)` -> commit (opt-in: INSERT -> commit -> `on_public_opt_in_changed(enabled=True)`). F2 disconnect (conforming): UPDATE `agent_delegations` -> `on_agent_disconnected` -> commit.
    - Grants naming a NEW row's random ID: `on_user_created` / `on_agent_delegated` (F2), `visibility.on_profile_created` (F5) and `on_question_created(question_id, profile_id, requester_user_id)` (F7). If the commit fails, their tuples name an ID no row, token or principal carries, so nothing can reach them; `--prune` removes them. They warn and return `None` while unconfigured and raise configured errors.
  - POST-COMMIT, only after the row is committed: grants on EXISTING users and profiles, `on_connection_granted(profile_id, viewer_user_id, tier)` (F6: writes `tier`, then deletes the other tier), `on_unblocked(profile_id, blocked_user_id)` (F6: deletes `blocked`, restores no tier) and `on_public_opt_in_changed(profile_id, enabled=True)` (F5). Called before commit, a later rollback would leave reachable access (a declined user connected, a blocked user back on Public, a private profile public). They never raise for OpenFGA errors or timeouts: they log an ERROR naming the hook and return `None`; access stays denied until `fga_reconcile` restores it. A rolled-back transaction never calls them, so it never grants.
  - F6 approval or tier change: `on_connection_tier_changing(tier=new)` before commit, `on_connection_granted(tier=new)` after. `profile_id` is the target's profile (the one who approved, declined or blocked); the viewer is the requester.
  - Residual: a post-commit grant delayed past a later revoke of the same row could land after the revoke's delete. Serialize changes to the same row: F6 per (requester, target) pair, F5 Public opt-in changes per profile (e.g. hold a per-row lock until the post-commit grant has run, or re-read the row after it). `fga_reconcile` repairs it either way.
- Checks are bounded and fail closed: each OpenFGA check (`can_contribute`, `can_respond`, `require_*`, the checks inside `resolve_viewer_tier` and so `visible_claims`/`owner_claims`, and inside `can_release_answer`) by `CHECK_TIMEOUT_SECONDS` (3s), a whole tier resolution by `TIER_RESOLUTION_TIMEOUT_SECONDS` (5s) and a whole `can_release_answer` by `ANSWER_RELEASE_TIMEOUT_SECONDS` (5s). Past either they raise `AuthorizationCheckTimeout` (a `TimeoutError`; never a grant or a lower tier); adapters map it to a generic 5xx like other OpenFGA errors. Hook bounds and post-commit grant semantics are unchanged.
- Question checks (F7), in `authz.py`, keyword-only `fga=None` (the configured client); unconfigured raises `FgaConfigurationError`, an inconsistent principal raises `AuthorizationDenied`:
  - `can_respond(principal, question_id)` / `require_respond(...)` (uniform `AuthorizationDenied`): a `respond` check on `question:<id>`, so only a connected agent of the asked-about profile's owner. Bounded by `CHECK_TIMEOUT_SECONDS`.
  - `can_release_answer(requester_principal, question_id, profile_id)` returns the requester's CURRENT `ViewerTier` on `profile_id`, or `None`. It checks, in order: `question:<id>#about@profile:<profile_id>` (a wrong `profile_id` gets `None`, never another profile's tier), `read_answer` for the principal (requester or requester's agent unless blocked; the owner side gets `only_me`), then `resolve_viewer_tier` is not `none` (the re-check that stops a revoked requester, since `read_answer` survives revocation). Bounded per check and overall by `ANSWER_RELEASE_TIMEOUT_SECONDS` (5s): a timeout raises `AuthorizationCheckTimeout`, never a tier or `None`. No PostgreSQL. The tier only bounds the release: F7 must ALSO confirm that every evidence claim is still in `visible_claims` for this requester and that the answer's audience rank is at most the tier.
- `backend/src/revel/auth/agent_disconnect.py`: `disconnect_agent(principal, delegation_id, *, resolver=None)` for F8 and the MCP tool. A user (`via="ui"`) may disconnect any of their own delegations; an agent may disconnect only itself (`delegation_id == principal.delegation_id`). It calls F2's `IdentityResolver.disconnect_delegation` with the principal's own `user_id`; every other case (an agent naming another delegation, another user's, unknown, already disconnected) raises the same `AuthorizationDenied`.
- `backend/src/revel/auth/visibility.py`: the only claim read paths. `visible_claims` (shared viewing for the owner and for others: OpenFGA resolves the tier, SQL keeps live facts whose audience rank fits it, so Only Me never reaches a non-owner; for non-owners the current policy's `share_provisional` gates provisional facts (returned with a caveat flag) and, for Public-only viewers, `public_opt_in` gates Public facts; tier `none` raises `AuthorizationDenied`; non-owners get `SharedClaim` projections without contributor, provenance or internal fields, the owner gets ORM claims) and `owner_claims` (owner/owner's agent management reads, all statuses). Also `on_profile_created` (F5's grant hook; writes only the owner tuple). `backend/tests/authz/test_claim_read_guard.py` fails if a module under `revel/api`, `revel/mcp` or `revel/services` references claims without them, queries claims directly (only modules in its `CLAIM_WRITE_MODULES` allowlist, F5's claim write services, may), or uses the private tier helpers or `ViewerTier.only_me`.
- Reconcile, explicitly: `uv run python -m revel.auth.fga_reconcile [--prune] [--min-age MINUTES] [--window MINUTES]` snapshots Postgres (REPEATABLE READ) and makes OpenFGA match it: owner, agent, connection tier (approved requests: the requester on the target's profile), blocked, Public opt-in (current policy) and question tuples. Rows changed within `--window` (default 2) are not re-granted (their hook just ran); revocations always apply. A short barrier transaction then locks, in this order, `connection_requests` (EXCLUSIVE), `contribution_policies` (EXCLUSIVE) and `agent_delegations` (SHARE), waiting for in-flight writers to commit: on the first two also `SELECT ... FOR UPDATE` row-lockers and claims/claim_events inserts (their foreign-key check on the policy); on `agent_delegations` only row writers, so the many inserts whose foreign key names a delegation never wait on it or deadlock with it. Plain SELECTs are never blocked. Nothing references `connection_requests`, and a delegation is locked last and only in SHARE, so with the current schema and the lock-order rule above no writer can hold what the barrier waits for while waiting on what it holds (`fga_reconcile._barrier` gives the argument). It then re-applies the current state of anything changed since the snapshot. Lock queues are FIFO, so app writers queue behind the barrier: its three lock waits together and each statement are limited to 3s (`lock_timeout`, `statement_timeout`) and its OpenFGA work under the lock to 3s, with 4 jittered attempts. If every attempt fails, reconcile raises `BarrierNotApplied`, skips `--prune` and the CLI exits 3 with "re-run reconcile" (step-2 re-grants of rows revoked after the snapshot may still be live). `--prune` deletes unjustified tuples of every non-owner relation older than `--min-age` (default 10) that a fresh read still does not justify. Idempotent; summary on stderr. The barrier needs the database role to have UPDATE on those tables (as the app role does).
- Bootstrap, explicitly (never at app startup), from `backend/`: `uv run python -m revel.auth.fga_bootstrap`. It uses `OPENFGA_STORE_ID` or finds/creates the store named `revel-gifts`, writes `model.json` only if it differs from the latest model, and prints only `OPENFGA_STORE_ID=` / `OPENFGA_AUTHORIZATION_MODEL_ID=` on stdout. Model path: `--model`, then `OPENFGA_MODEL_PATH`, then `../authorization/model.json` from the working directory (image layout), then the repository path. `--check` is a read-only probe printing `unconfigured` or `healthy` (exit 0), non-zero otherwise.
- Integration tests (`pytest -m openfga`) need a real server; see `backend/tests/authz/test_authz_openfga.py` for the isolated compose command. They skip unless `OPENFGA_TEST_API_URL` is set and reachable.
